# 겪었던 문제와 해결 과정 (Troubleshooting & Improvement)

## 🧐 문제 상황 1: 직원 회원가입 시 발생하는 간헐적인 500 에러

**증상**: 관리자가 매장을 생성한 후, 직원이 해당 매장을 선택하고 회원가입을 시도하면, 때때로 `ORA-02291: 부모 키가 없습니다` 라는 500 에러가 발생하며 가입에 실패했습니다.

### 💡 해결 과정: 중복 데이터 생성 로직 식별 및 제거

1.  **초기 가설**: 처음에는 프론트엔드에서 선택한 매장의 `store_id`가 백엔드로 제대로 전달되지 않는 문제라고 추측했습니다.
2.  **데이터 직접 확인**: `Alert`와 `console.log`를 사용하여 API 호출 직전의 데이터를 확인한 결과, `store_id`는 정상적으로 포함되어 있었습니다.
3.  **백엔드 로그 재분석**: 에러가 "간헐적으로" 발생한다는 점에 착안하여 백엔드 로그를 다시 분석한 결과, **관리자 회원가입(`signupAPI`)** 시, 프론트엔드에서 **`registerStoreAPI`를 중복으로 호출**하고 있었음을 발견했습니다.
4.  **근본 원인 파악**: 이 중복 호출로 인해, 관리자 가입 시 이름이 똑같은 '정상 매장(A)'과 '유령 매장(B)'이 동시에 생성되었습니다. 직원이 가입 시 우연히 '유령 매장(B)'을 선택하면, `STORE` 테이블에 존재하지 않는 `store_id`로 `STORE_MEMBER`를 생성하려다 "부모 키 없음" 에러가 발생했던 것입니다.
5.  **해결**: 관리자 회원가입 로직을 수정하여, 매장 정보를 포함한 `signupAPI` **단 한 번만 호출**하도록 하여 중복 데이터 생성을 원천 차단했습니다.

### ✨ 개선 결과 및 효과

- 데이터의 흐름과 백엔드 로직을 깊이 있게 분석하여, 눈에 보이지 않는 데이터 불일치 문제를 해결하고 회원가입 기능의 안정성을 100% 확보했습니다.
- 프론트엔드와 백엔드 간의 API 호출 책임을 명확히 하여, 향후 유사한 문제가 발생하지 않도록 구조를 개선했습니다.

## 🧐 문제 상황 2: 로컬 개발 환경의 백엔드 서버와 모바일 앱 간의 통신 부재

실제 모바일 기기나 에뮬레이터에서 실행되는 네이티브 앱은 `localhost`로 실행 중인 백엔드 서버에 직접 접근할 수 없습니다. LINE 로그인 콜백과 같이 외부 서비스가 로컬 서버에 접근해야 하는 경우, 이 문제를 반드시 해결해야 했습니다.

### 💡 해결 과정: 터널링 서비스 도입 및 문제 해결

1.  **터널링 서비스 도입 결정**: 로컬 서버를 외부 인터넷에 노출시켜주는 터널링 서비스 도입을 결정하고, 초기에는 `cloudflared`를 사용하기로 했습니다.
2.  **`cloudflared` 연결 실패 문제 발생**: `cloudflared tunnel` 명령어를 실행했으나, 모바일 앱 및 웹 브라우저에서 터널 주소로 접속 시 "서버를 찾을 수 없음" 오류가 지속적으로 발생했습니다.
3.  **체계적인 원인 분석**:
    *   **1차 가설 (방화벽/백신):** Windows 방화벽 및 백신 프로그램(알약)을 잠시 비활성화하고 테스트했으나, 문제가 해결되지 않았습니다. 이를 통해 OS 수준의 보안 프로그램이 직접적인 원인은 아님을 확인했습니다.
    *   **2차 가설 (실행 순서):** 백엔드 서버가 완전히 실행된 후 터널을 실행하는 순서를 지켰으나, 여전히 연결에 실패했습니다.
    *   **3차 가설 (주소 해석):** `localhost` 대신 IP 주소 `127.0.0.1`을 직접 사용하여 터널을 실행했으나, 동일한 문제가 발생했습니다.
    *   **최종 결론**: `cloudflared` 프로그램이 현재 사용자의 PC 네트워크 환경(ISP, 공유기 설정 등) 또는 특정 시스템 드라이버와 호환성 문제가 있는 것으로 최종 판단했습니다.
4.  **대안 솔루션 `ngrok`으로 전환**:
    *   가장 대중적이고 안정적인 터널링 서비스인 `ngrok`으로 대안을 전환했습니다.
    *   `ngrok` 설치, 계정 인증(`authtoken` 등록) 후 `ngrok http 8080` 명령어로 터널을 실행하자, **즉시 연결에 성공**했습니다.
5.  **전체 환경 통일**: 성공적으로 생성된 `ngrok`의 공개 주소를 기준으로, 관련된 모든 설정을 통일했습니다.
    *   **프론트엔드**: `native/api/auth.ts`의 `baseURL`을 `ngrok` 주소로 변경.
    *   **백엔드**: `application.properties`의 `line.login.redirect-uri` 값을 `ngrok` 주소로 변경하도록 요청.
    - **LINE 서버**: LINE Developers Console의 Callback URL을 `ngrok` 주소로 변경하도록 요청.

### ✨ 개선 결과 및 효과

- 복잡한 네트워크 호환성 문제에 대해 체계적인 가설 수립과 검증을 통해 원인을 분석하고, 특정 도구에 얽매이지 않는 대안 솔루션(`ngrok`)으로 신속하게 전환하여 문제를 해결했습니다.
- 이를 통해 외부 서비스(LINE)와의 연동이 필요한 기능을 안정적으로 개발하고 테스트할 수 있는 환경을 성공적으로 구축했습니다.

## 🧐 문제 상황 3: 프론트엔드-백엔드 간 API 명세 불일치

개발 초기 단계에서 정의된 프론트엔드의 API 함수(`native/api/auth.ts`)와 실제 백엔드 컨트롤러의 API 명세(URL, 파라미터 등)가 일치하지 않는 부분이 다수 존재했습니다. 이로 인해 API 호출 시 404 에러나 파라미터 관련 오류가 발생할 위험이 있었습니다.

### 💡 해결 과정: API 명세 전수조사 및 동기화

1.  **백엔드 컨트롤러 코드 분석**: `UserC.java`, `StoreC.java` 등 백엔드의 모든 컨트롤러 파일을 직접 분석하여 `@RequestMapping`, `@GetMapping`, `@PostMapping`, `@RequestParam`, `@RequestBody` 등의 어노테이션을 통해 정확한 API 명세를 파악했습니다.
2.  **`auth.ts` 파일 전체 리팩토링**: 파악된 명세를 바탕으로, `auth.ts` 파일의 모든 API 함수를 실제 백엔드와 100% 일치하도록 수정했습니다.
    - 잘못된 URL 경로 및 파라미터 전달 방식(Query String vs. Path Variable)을 수정했습니다.
    - 백엔드에 존재하지 않거나 중복되는 API 함수는 하단에 주석으로 명확하게 분리하여 정리했습니다.
    - 각 API 함수 그룹 상단에 관련 컨트롤러 파일명을 주석으로 추가하여, 향후 유지보수 시 백엔드 코드를 쉽게 찾아갈 수 있도록 가독성을 높였습니다.

### ✨ 개선 결과 및 효과

- 프론트엔드와 백엔드 간의 API 명세 불일치 문제를 완전히 해소하여, 통신 오류 발생 가능성을 사전에 차단하고 개발 안정성을 높였습니다.
- 명확한 주석과 정리된 구조를 통해, 신규 팀원이나 다른 개발자가 코드를 이해하고 유지보수하기 쉬운 환경을 만들었습니다.

## 🧐 문제 상황 4: 일관성 없는 다크 모드 UI와 유지보수의 어려움

프로젝트 초기 단계에서는 각 화면과 컴포넌트에서 개별적으로 다크 모드 스타일을 처리했습니다. 이로 인해 다음과 같은 문제점들이 발생했습니다.

1.  **UI 버그**: 다크 모드로 전환 시, 일부 텍스트는 검은색으로 그대로 남아 보이지 않거나, 특정 아이콘 및 배경색이 라이트 모드 색상으로 표시되는 등 **UI의 일관성이 깨지는 문제**가 빈번하게 발생했습니다.
2.  **코드의 복잡성 증가**: 스타일을 적용하기 위해 모든 컴포넌트에 `isDarkMode` prop을 전달해야 했고, `StyleSheet` 내부에서는 삼항 연산자(`isDarkMode ? 'white' : 'black'`)를 남발하여 코드가 지저분하고 가독성이 떨어졌습니다.
3.  **유지보수의 어려움**: "앱의 전체적인 브랜드 색상을 파란색에서 보라색으로 바꿔주세요" 와 같은 간단한 디자인 변경 요청이 들어왔을 때, 관련된 모든 파일을 찾아 수십 개의 색상 코드를 일일이 수정해야 하는 **비효율적인 유지보수 구조**를 가지고 있었습니다.

## 💡 해결 과정: 중앙화된 테마 시스템 도입 및 전체 리팩토링

이 문제를 근본적으로 해결하기 위해, **의미 기반의 중앙화된 테마 시스템**을 도입하고 전체 코드를 리팩토링하는 과정을 거쳤습니다.

### 1단계: 중앙 색상 관리소 `ThemeContext` 설계

- `contexts/ThemeContext.tsx` 파일을 생성하여 앱의 모든 색상을 한 곳에서 관리하도록 했습니다.
- 단순히 'dark', 'light'로 구분하는 것을 넘어, 색상의 **의미(Semantic Name)**에 따라 변수명을 정의했습니다.
  - **Before**: `const color = isDarkMode ? '#E0E0E0' : '#333333';`
  - **After**: `text: isDarkMode ? '#E0E0E0' : '#333333',` -> `color: colors.text`
- `primary`, `background`, `card`, `border`, `text`, `subText` 등 기본적인 색상뿐만 아니라, `sunday` (일요일 텍스트 색상), `disabled` (비활성화 버튼 색상), `yellowLight` (경고 배지 배경색) 등 특정 상태나 컴포넌트에 사용되는 색상까지 모두 변수화했습니다.

### 2단계: 전수조사를 통한 하드코딩 색상 제거

- `screens`와 `components` 폴더 내의 **모든 `.tsx` 파일을 하나씩 검토**하며, 하드코딩된 색상 코드를 찾아냈습니다.
- 찾아낸 모든 색상 값을 1단계에서 정의한 `ThemeContext`의 `colors` 객체 변수로 교체했습니다.
- 이 과정에서 불필요하게 `isDarkMode` prop을 받던 모든 컴포넌트에서 해당 prop을 제거하고, 대신 `useTheme()` 훅을 직접 사용하도록 코드를 통일했습니다.

### 3단계: 동적 스타일링 구조 통일

- 모든 컴포넌트가 `const { colors } = useTheme();` 와 `const styles = getThemedStyles(colors);` 패턴을 따르도록 하여, 스타일링 코드의 일관성을 확보했습니다.
- 이를 통해 어떤 개발자가 어떤 파일을 보더라도 테마와 스타일이 어떻게 적용되는지 쉽게 파악할 수 있게 되었습니다.

## ✨ 개선 결과 및 효과

- **완벽한 UI 일관성 확보**: 앱의 모든 부분에서 다크 모드가 완벽하게 동작하게 되어 사용자 경험(UX)의 질을 크게 향상시켰습니다.
- **유지보수 비용 극감**: 이제 "브랜드 색상을 바꿔주세요" 라는 요청이 와도 `ThemeContext.tsx` 파일의 `primary` 색상 값 **단 한 줄만 수정**하면 앱 전체에 일괄적으로 반영됩니다. 이는 개발 속도와 유지보수 효율성을 극적으로 향상시켰습니다.
- **코드 가독성 및 품질 향상**: 불필요한 prop 전달과 삼항 연산자가 사라지고, 의미 있는 변수명을 사용하게 되어 코드 전체의 가독성과 품질이 높아졌습니다. 이는 향후 신규 팀원이 프로젝트에 적응하는 데 드는 시간도 단축시키는 효과를 가져옵니다.
